# Plataforma UFJ — Fatia 1: plano de implementação

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Objetivo:** o dono importa os planos de ensino das matérias, liga os slides aos tópicos, abre a tela de preparação de cada avaliação e estuda cada tópico com sessões nativas de Ensinar e Praticar já ligadas ao plano, com a IA respondendo em português.

**Arquitetura:**
- A biblioteca é um conjunto de arquivos JSON em `<LH_DATA_DIR>/biblioteca/`, com tipos e validação em `src/core`, o adaptador em `src/store` e os serviços em `src/server`.
- O plano em PDF vira texto pela `convertPdf` que já existe e passa por uma única chamada de modelo com uma ferramenta de envio (`runSubmitAgent`). O resultado volta como rascunho para revisão e nada é salvo sem ela.
- As sessões nascem pela `POST /api/chats` com um marcador novo, `ufj-context`, irmão do `graph-context`. O campo de mensagem já vem preenchido, pelo caminho `stashOpeningPrompt(id, text, true)`.

**Tecnologias:** Next.js 16 (rotas `app/api/**`, páginas `app/**`), React 19, Tailwind v4, TypeBox, testes `node:test` com `tsx`, Electron e electron-builder.

**Spec:** [`docs/superpowers/specs/2026-11-18-ufj-etapa-a-design.md`](../specs/2026-11-18-ufj-etapa-a-design.md). Esta fatia cobre as seções 7.2 a 7.6, 7.12 (só o fragmento de idioma, o de contexto e as linhas em português dos workers) e 7.14. Provas, simulados e caderno de erros ficam para as fatias 2 e 3. A tradução dos prompts existentes fica para a fatia 1.5.

## Restrições globais

- **Idioma:**
  - Todo texto novo que o aluno vê é em português do Brasil.
  - Todo texto novo que o modelo lê também é em português: prompts, descrições de ferramentas, mensagens de erro para o modelo e o texto dos marcadores.
  - Identificadores de código seguem o estilo do arquivo onde estão. Campos dos dados da biblioteca usam os nomes em português da spec (seção 7.2).
- **Formato:** toda raiz JSON da biblioteca tem `"formato": 1`. Formato maior que 1 é recusado na leitura. A escrita é sempre atômica (`writeFileAtomicSync`), com indentação `"\t"` e quebra de linha final.
- **Revisão humana:** nenhum resultado do modelo é gravado na biblioteca sem passar por uma tela de revisão (spec, 3).
- **Fronteiras de importação** (`eslint.config.mjs:38-71`):
  - `components/` importa só `src/core/index.ts`;
  - `app/` importa só `src/core/index.ts`, `src/server/index.ts` e `lib/*`;
  - `src/core` não importa agent, server nem store;
  - `src/agent` não importa server nem store.
- **Dados de teste:** fixtures e testes usam **nomes fictícios** ("Prof. Exemplo", "Disciplina Teste"), porque o repositório é público. Os planos reais do dono nunca entram no Git.
- **Variáveis de ambiente em testes:** `LH_DATA_DIR` e `LH_AUTH_FILE` apontam para `fs.mkdtempSync(...)` **antes** de qualquer `await import(...)` de config, stores ou rotas (o padrão de `tests/source-organization-route.test.ts:8-17`).
- **Next.js:** antes de escrever rotas e páginas, ler `node_modules/next/dist/docs/` sobre route handlers e `params` assíncronos (tarefa 0). Copiar os padrões de `app/api/graph/render-settings/route.ts` e `app/plugins/[pluginId]/[viewId]/page.tsx`.
- **Comandos de verificação:** `npm test`, `npm run typecheck`, `npm run lint`.

## Foco da revisão

As cinco situações que a spec implica, nenhum teste óbvio cobriria e mais devem aparecer no uso real. Cada uma tem teste na tarefa dona do código.

1. **"Faltam N dias" errado por fuso horário.** `new Date("2026-12-08")` é meia-noite UTC, que é 21h do dia anterior em Brasília. O esperado é contar por datas locais. Teste na tarefa 9.
2. **Avaliação sem data e sem aula marcada no cronograma.** O esperado é escopo vazio com aviso na revisão, nunca um escopo inventado. Teste na tarefa 3.
3. **Reimportar uma turma que já existe.** O esperado é responder 409 sem `substituir`. Ao substituir, os ids de tópico usados por sessões continuam valendo: os removidos viram `arquivado`. Teste na tarefa 6.
4. **JSON corrompido ou de formato mais novo na biblioteca.** O esperado é listar as outras matérias e mostrar o problema, sem quebrar a página. Teste na tarefa 4.
5. **Sessão criada para um tópico que depois foi arquivado, ou com ids desconhecidos.** A `POST /api/chats` com ids desconhecidos responde 400. Uma sessão antiga continua abrindo, e o cartão do contexto se mostra com os nomes guardados no próprio marcador. Testes nas tarefas 8 e 11.

### Tarefa 3: Escopo, posições e reconciliação de tópicos (spec 7.2–7.3)

**Arquivos:**
- Criar: `src/core/biblioteca-escopo.ts`, exportado no barrel.
- Teste: `tests/biblioteca-escopo.test.ts`

**Interfaces:**
- **`computePosicoes(avaliacoes: Avaliacao[], aulas: Aula[]): Avaliacao[]`.** Atribui `posicao` 1, 2, 3… às avaliações de tipo `prova-escrita` ou `prova-pratica`, na ordem da posição no cronograma. As outras ficam sem posição.
- **`computeEscopos(avaliacoes: Avaliacao[], aulas: Aula[]): { avaliacoes: Avaliacao[]; avisos: string[] }`.** O algoritmo:
  1. A posição de uma avaliação no cronograma é a `ordem` da primeira aula com `avaliacaoId === id`.
  2. Se não houver essa aula, é a `ordem` da última aula com `data <= avaliacao.data`.
  3. Se não houver nem uma coisa nem outra, a posição é desconhecida: escopo `[]` e o aviso "A avaliação {id} não tem data nem aula no cronograma: defina o escopo à mão."
  4. Prova regular: os tópicos das aulas com `ordem` maior que a posição da prova regular anterior e menor que a posição desta, sem repetir, na ordem da primeira aparição.
  5. `substitutiva` e `recuperacao`: todos os tópicos das aulas.
  6. Outros tipos: `[]`.
- **`reconcileTopicos(existentes: Topico[], propostos: { ref: string; titulo: string; descricao?: string; existente: boolean }[], aulas: { topicos: string[] }[]): { topicos: Topico[]; aulas: string[][]; erros: string[] }`.**
  - Um `ref` com `existente: true` precisa estar entre os ids existentes; se não estiver, gera erro.
  - Um `ref` novo ganha o id `slugify(titulo)`. Se colidir, usa sufixos `-2`, `-3`…
  - Os existentes não citados continuam como estão.
  - O resultado `aulas` traz os tópicos de cada aula trocados pelos ids finais.
- **`topicosReferenciados(turmas: Turma[], refsDeSessoes: string[]): Set<string>`.**
- **`arquivarRemovidos(antes: Topico[], depois: Topico[], referenciados: Set<string>): Topico[]`.** Um tópico de `antes` que sumiu de `depois` mas está em `referenciados` volta com `arquivado: true`. Os ids são imutáveis.
